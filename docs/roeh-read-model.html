Trace, map & bloom — how a decision record answers a question

Three files, one job: answer “why did we decide X, and is it still true?” without reading a 200 KB log — and without a keyword search silently missing the entry that overturned the one you found.

Where the three come from

decision-trace.md
The authority
The append-only log. Every entry ever written, in order — the single source of truth.
  • Only ever grows
  • Keeps superseded entries ([REVERSAL], [CORRECTION])
  • Too big to read whole past ~400 KB
◆ everything else is derived from this
…-map.md
The live index
A collapsing projection held to a token budget — “what’s true now,” not the whole history.
  • One line per live entry
  • A ledger of reversals, conflicts, dead-ends
  • Retired regions collapse to headers
…-bloom.json
The no-miss filter
A per-region filter over literal words — so summarizing into the map can never lose a lookup.
  • “Which regions contain word X?”
  • No false negatives — never skips a match
  • Bigger than the map: it indexes every token
trace  —  roeh map  —▶  regenerates  map  +  bloom ·  both are a disposable, gitignored cache — blow them away and rebuild from the trace anytime
Same record, three sizes — this is the whole point
trace197 KB
bloom44 KB
map6 KB

The Oracle reads the 6 KB map, not the 197 KB trace — and still can’t miss a relevant entry, because the bloom decides what to pull, not a summary’s judgment. (Figures from a representative live trace.)

One question, four steps

The question
“Do we still block a manual /compact?”

A plain keyword search is a trap here: the record holds an old decision (“manual blocks, exit 2”) that was later reversed. Grep finds the old one and reads it as current. Here’s how the three files avoid that:

roeh verifymaptrace

Is the map current?

Hashes the log’s bytes — even an uncommitted append counts. If the map has fallen behind the trace, stop and rebuild with roeh map. You never read from a stale summary.

What’s live, and what got overturned?

The map lists only live entries plus a ledger of reversals. It shows the current stance and flags that an earlier decision on this was superseded — the thing grep can’t know.

Which regions could hold the answer?

Tokenizes the question and asks each region’s bloom. It returns every region that could match — with no misses: both the region with the original decision and the region with its reversal.

→regions R2 (original) + R7 (reversal) — 2 of many

Reads only those regions from the trace, at full fidelity, with read-closure — an entry arrives together with the reversal that supersedes it, so you can’t quote the dead one by accident.

Why not the two obvious shortcuts

✕
Read the whole trace
Fine at first, impossible later. Past ~400 KB it blows the budget, and it’s mostly superseded sediment — old decisions, reversed §5 blocks — that buries the live answer.
✕
grep the trace
Cheap, and silently wrong. You can’t search for what you don’t know to look for, and a keyword hit on the original decision reads exactly like a hit on the live one — the reversal two chapters down never surfaces.
✓
map + bloom + trace
map gives the live picture in a tiny read · bloom guarantees every region that could match gets drilled · trace supplies the exact text on demand. Small read, no misses, full fidelity — and roeh verify makes sure you’re never reading a stale view.

In one line: the trace is the truth (too big to read whole), the map is the live index you actually read, and the bloom is the safety net that makes summarizing into the map safe. A read walks verify → map → scope (bloom) → read (trace).
